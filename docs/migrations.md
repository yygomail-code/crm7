# Миграции БД CRM7

Изменения схемы БД едут вместе с кодом: файлы `api/db/migrations/NNN_*.sql`
попадают в образ, а на сервере `api/bin/migrate.php` накатывает только новые
(учёт — в таблице `schema_migrations`). Существующие данные при этом не
затрагиваются.

## Жёсткие правила

1. **Новое изменение — новый файл.** Уже применённую миграцию редактировать
   нельзя: она учитывается по имени и повторно не выполнится. Правка = новый
   номер.
2. **Сначала аддитивно, удаление — позже.** Новые таблицы/колонки добавляем
   свободно. Удаление объекта — отдельным релизом, когда код уже перестал его
   использовать (см. expand/contract ниже).
3. **Один файл — одно логическое изменение.** Транзакций и down-миграций нет:
   если файл упадёт посередине, часть запросов уже применится. Делайте запросы
   идемпотентными (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`,
   `DROP ... IF EXISTS`).
4. **Бэкап перед деплоем на k/prod** — обязателен. Откат схемы автоматически
   невозможен.
5. **Сиды только для demo.** `seed-demo.php --force` полностью очищает таблицы;
   на k/prod он не запускается никогда. Полный сброс demo —
   `/srv/projects/crm7-demo/reset-demo.sh`.
6. **Проверка на `test`.** Любую миграцию сначала прогоняем на `test.crm7.ru`,
   затем на `k`, затем на проде клиента.

## Команды

```bash
php api/bin/migrate.php                     # применить ожидающие
php api/bin/migrate.php --status            # показать применённые/ожидающие
php api/bin/migrate.php --allow-destructive # разрешить DROP/TRUNCATE/DELETE
```

`--status` безопасен (только чтение). Без `--allow-destructive` скрипт
**отказывается** применять миграции, содержащие `DROP TABLE|COLUMN|DATABASE`,
`TRUNCATE` или `DELETE FROM`.

## Совместимость и откат (expand/contract)

Схема каждого релиза должна работать и с новым, и с предыдущим кодом — тогда
откат образа по тегу не ломается.

### Новая таблица / колонка — безопасно
```sql
-- 036_client_tags.sql
CREATE TABLE IF NOT EXISTS `client_tags` (...);
ALTER TABLE `users` ADD COLUMN IF NOT EXISTS `telegram` VARCHAR(64) NULL;
```

### Переименование колонки — в 2–3 релиза
1. Добавить `new_col`, бэкфилл `UPDATE ... SET new_col = old_col`, код читает новое.
2. Позже — удалить `old_col` (уже никто не использует).

### Удаление колонки/таблицы — только отдельным поздним релизом
1. Релиз N: код перестал использовать объект; миграция ничего не удаляет.
2. Релиз N+1 (после наблюдения): `ALTER TABLE ... DROP COLUMN old_col` с
   `--allow-destructive` и бэкапом.

Нельзя в одном релизе одновременно убрать использование и удалить объект:
откат кода сломается.

## Что НЕ теряется при обновлении

- Данные пользователей и наработки клиента — в томе `data/db`, вне образа.
- Вложения — в томе `app/api/storage`.
- Конфиг окружения — в `app/api/config/.env` (в образ не входит).

Обновление образа меняет только код; миграции добавляют схему инкрементально.
Перенос данных между окружениями (например, k → прод клиента) — отдельный
`mysqldump`/restore, а не обновление образа.
